### C17 — X-Family-Id jamais envoyé sur les routes /api/families/{familyId}/… : toutes les collections métier retournent 400

**Gravité** : P0 · **Axe** : reseau-repos · **Emplacement** : `mobile/lib/core/network/interceptors/api_routes.dart:14`
· **Contrat** : CLAUDE.md — invariant « Scope famille obligatoire : toute ressource métier est scopée à la famille active via le header X-Family-Id » ; cdc §3.6 ; specs/lots (Lots 1 à 6).

**Preuve.** `ApiRoutes.isFamilyScoped()` exclut du scope **tout** chemin contenant `/api/families` :
```dart
if (path.contains('/api/families')) return false;   // ligne 14
if (path.contains('/api/invitations')) return false; // ligne 15
```
Or `contracts/openapi.json` place la quasi-totalité des ressources métier sous ce préfixe : `/api/families/{familyId}/members`, `/children`, `/events`, `/exchanges`, `/custody/{days,pattern,stats,exceptions}`, `/holidays`, `/links`, `/invitations`, `/overlay-preferences`. `FamilyScopeInterceptor` (family_scope_interceptor.dart:26) ne pose donc jamais l'en-tête pour ces appels, et aucun dépôt ne le compense (tous documentent « le scope X-Family-Id est posé par l'intercepteur réseau » — agenda_repository.dart:12, custody_repository.dart:9, members_repository.dart:10, children_repository.dart:10, exchanges_repository.dart:10, overlay_repository.dart:41).
Côté serveur, `backend/src/Security/FamilyScope.php:59-62` lève `FamilyScopeRequiredException` (HTTP 400, `/errors/family-scope-required`) dès que l'en-tête est absent, et **tous** les providers/processors de ces routes appellent `$this->scope->require()` : `FamilyMembersProvider.php:32`, `AgendaAccess.php:25-43` (utilisé par `EventsProvider`), `InvitationsProvider.php:33`, `RevokeInvitationProcessor.php:37`, `CustodyAccess`, `ExchangeAccess`. Les tests fonctionnels backend confirment que l'en-tête est obligatoire (`tests/Functional/EventApiLot4Test.php:44`, `CustodyApiLot3Test.php:38`, `FamilyManagementTest.php:38`).
Le test Flutter qui prétend couvrir ce cas utilise une route inexistante (`test/core/network/interceptors_test.dart:31` : `dio.get('/api/custody')`), ce qui masque totalement le défaut : aucun test n'exerce un chemin réel `/api/families/…`.

**Panne.** Utilisateur connecté, famille active sélectionnée, il ouvre l'onglet Agenda (ou Garde, Enfants, Échanges, Membres, Réglages › Invitations). `familyEventsProvider` → `AgendaRepository.listEvents()` → `GET /api/families/<uuid>/events` **sans** `X-Family-Id` → le backend répond 400 `application/problem+json` `{"type":"/errors/family-scope-required","detail":"Le header X-Family-Id est requis pour cette ressource."}`. `ReadCache.list` voit `e.response != null` et propage l'`ApiException` (aucun repli cache), l'écran affiche le bandeau d'erreur. Idem pour la création d'événement, la liste des membres, l'invitation d'un membre, le rythme de garde, la liste des échanges, les préférences overlay : **aucun écran métier de l'app mobile ne fonctionne**. Hors ligne c'est pire encore : la mutation part en outbox avec le `X-Family-Id` figé (agenda_repository.dart:80), donc la création différée passe — mais la lecture en ligne échoue.

**Correction proposée.** Inverser la logique : ne dé-scoper que les chemins réellement non scopés, par correspondance **exacte ou par préfixe complet de segment**, et non par `contains`. Par exemple :
```dart
static bool isFamilyScoped(String path) {
  if (isAuthRoute(path)) return false;
  if (path == '/api/families') return false;              // collection : liste/création
  if (RegExp(r'^/api/families/[^/]+$').hasMatch(path)) return false; // détail famille
  if (path == '/api/me' || path.startsWith('/api/me/')) return false;
  if (path == '/api/invitations/accept') return false;
  if (path.startsWith('/api/docs')) return false;
  return true;
}
```
Et remplacer le test `dio.get('/api/custody')` par une **table de cas issue de `contracts/openapi.json`** (chaque chemin du contrat + attendu scopé/non scopé), pour que toute divergence entre le contrat et l'intercepteur casse la CI.

**Vérification adversariale.** Vérifié de bout en bout. `mobile/lib/core/network/interceptors/api_routes.dart:14` fait bien `if (path.contains('/api/families')) return false;` et `FamilyScopeInterceptor.onRequest` (family_scope_interceptor.dart:26) ne pose donc jamais `X-Family-Id` pour ces chemins. Le client généré émet littéralement ces chemins (`lib/api/generated/clients/child_client.g.dart:111` `/api/families/${familyId}/children`, `custody_pattern_client.g.dart:34`, `exchange_client.g.dart:123`, `family_link_client.g.dart:34`…), et `dioProvider` (core/network/network_providers.dart:41) n'ajoute aucun autre mécanisme : `grep X-Family-Id lib/` hors code généré ne montre aucun dépôt qui poserait l'en-tête à la main (seul l'outbox le fige, outbox_service.dart:80). Côté serveur, `backend/src/Security/FamilyScope.php:59-62` lève `FamilyScopeRequiredException` dès que l'en-tête est absent — le `familyId` du chemin n'est utilisé qu'en contrôle de cohérence (familyIdFromPath, ligne 67), jamais en repli — et `require()` est bien appelé par `FamilyMembersProvider.php:32`, `InvitationsProvider.php:33`, `RevokeInvitationProcessor.php:38`, `AgendaAccess.php:25/31/40`, `CustodyAccess.php:27/33/45`. `ReadCache.list` (core/sync/read_cache.dart:53-56) propage bien l'`ApiException` quand `e.response != null` : aucun repli cache sur un 400. Le seul test du garde-fou (`test/core/network/interceptors_test.dart:31`) utilise `/api/custody`, chemin absent de `contracts/openapi.json` : rien ne couvre un chemin réel. Défaut réel, non couvert, et non documenté dans PROGRESS.md.

**Rectification du vérificateur.** Deux précisions. (1) La casse n'est pas totale : les routes item-level qui ne contiennent pas `/api/families` (`/api/events/{id}`, `/api/children/{id}`, `/api/notes/{id}`, `/api/exchanges/{id}`, `/api/exchanges/{id}/messages`, `/api/holidays/{id}/rule`, `/api/realtime/token`) reçoivent bien l'en-tête ; ce sont toutes les collections et créations sous `/api/families/{familyId}/…` qui partent nues — ce qui suffit à rendre inutilisable chaque écran métier (liste agenda, garde, enfants, échanges, membres, invitations, liens, préférences overlay). (2) « Hors ligne c'est pire encore » est inexact : le chemin hors-ligne est justement le seul qui fonctionne, l'outbox figeant `X-Family-Id` (agenda_repository.dart:80 → outbox_service.dart:49/80) et l'intercepteur donnant la priorité à cet `extra` (family_scope_interceptor.dart:20-24). Gravité relevée à P0 : ce n'est pas un parcours cassé mais la totalité des écrans métier en ligne.

### C4 — Permission INTERNET absente du manifeste Android principal : l'app est totalement inopérante en build release

**Gravité** : P1 · **Axe** : securite-auth · **Emplacement** : `mobile/android/app/src/main/AndroidManifest.xml:1`

**Preuve.** Le manifeste principal ne déclare aucune `<uses-permission android:name="android.permission.INTERNET"/>`. Elle n'est présente que dans `mobile/android/app/src/debug/AndroidManifest.xml` et `mobile/android/app/src/profile/AndroidManifest.xml` (générés par le template Flutter, « required for development »). Vérifié aussi côté plugins : aucune dépendance ne l'apporte par fusion de manifeste — `connectivity_plus-7.1.1` ne déclare que `ACCESS_NETWORK_STATE`, `app_links-7.0.0`, `flutter_secure_storage-9.2.4`, `path_provider_android`, `sqlite3_flutter_libs` n'en déclarent aucune. Corollaire du même fichier : aucun `android:usesCleartextTraffic` ni `android:networkSecurityConfig`, alors que la valeur par défaut documentée est `http://10.0.2.2:8000` (mobile/lib/core/config/app_config.dart:10) — le trafic en clair est bloqué par défaut depuis targetSdk 28, y compris en debug.

**Panne.** `flutter build apk --release` (ou l'`.ipa`/AAB produit par le pipeline du Lot 9), installation sur un téléphone : à l'écran de connexion, `POST /api/auth/login` échoue immédiatement (création de socket refusée, faute de permission) → `DioExceptionType.connectionError` → 3 retries → bannière « Connexion impossible. Verifiez votre reseau. ». Aucun écran de l'application n'est atteignable, sur un réseau parfaitement fonctionnel. Le défaut est invisible en développement et en CI puisque les manifestes debug/profile, eux, portent la permission.

**Correction proposée.** Ajouter `<uses-permission android:name="android.permission.INTERNET"/>` dans `android/app/src/main/AndroidManifest.xml` (au niveau `<manifest>`). Ajouter en complément un `network_security_config.xml` référencé par `android:networkSecurityConfig` qui n'autorise le trafic en clair que pour `10.0.2.2`/`localhost` en debug, le release restant HTTPS strict, et faire échouer le build release si `API_BASE_URL` n'est pas passé en `--dart-define` (plutôt qu'un repli silencieux sur l'URL de dev).

**Vérification adversariale.** Vérifié : mobile/android/app/src/main/AndroidManifest.xml (lu intégralement, 48 lignes) ne contient aucune `<uses-permission>` — la permission INTERNET n'apparaît que dans `src/debug/AndroidManifest.xml` et `src/profile/AndroidManifest.xml`. J'ai contrôlé indépendamment la fusion de manifeste : un balayage des 6 manifestes `android/src/main/AndroidManifest.xml` des paquets résolus dans `mobile/.dart_tool/package_config.json` ne trouve AUCUNE déclaration d'INTERNET — aucun plugin ne l'apporte. Un `flutter build apk/appbundle --release` produit donc un artefact sans permission réseau : toute création de socket lève une SecurityException, remontée par Dio en `DioExceptionType.connectionError`, rejouée 3 fois par le RetryInterceptor puis affichée « Connexion impossible. Verifiez votre reseau. » (api_exception.dart:110-114) — plus aucun écran authentifié n'est atteignable. Invisible en dev et en CI (le job `mobile` ne fait que `flutter test`, et les manifestes debug/profile portent la permission).

**Rectification du vérificateur.** Le volet secondaire sur le trafic en clair est moins solide que le volet INTERNET : `android:usesCleartextTraffic` par défaut à `false` vaut pour `targetSdk >= 28`, mais l'AGP injecte `usesCleartextTraffic="true"` dans les variantes debuggables, ce qui explique que `http://10.0.2.2:8000` fonctionne en debug ; le durcissement (network_security_config + échec du build release sans `--dart-define=API_BASE_URL`) reste une bonne recommandation, mais ce n'est pas un défaut observable aujourd'hui, contrairement à la permission manquante.

### C63 — Android release : permission INTERNET absente du manifeste principal — aucune requête réseau ne part d'un APK/AAB release

**Gravité** : P1 (annoncée P0) · **Axe** : tests-conformite · **Emplacement** : `mobile/android/app/src/main/AndroidManifest.xml:2`
· **Contrat** : CLAUDE.md § Découpage en lots (chaque lot livré en web ET mobile) ; cdc §9 DoD (écrans mobiles fonctionnels)

**Preuve.** Le manifeste principal ne contient aucun `<uses-permission>` : la seule déclaration de `android.permission.INTERNET` vit dans `android/app/src/debug/AndroidManifest.xml` et `android/app/src/profile/AndroidManifest.xml` (héritage brut du template Flutter). Ces deux fichiers ne sont fusionnés que pour les variantes debug/profile. Vérifié côté plugins : sur les 6 plugins Android résolus (`.flutter-plugins-dependencies`), seul `connectivity_plus` déclare une permission, et c'est `ACCESS_NETWORK_STATE` — aucun ne déclare INTERNET. Le manifeste fusionné d'une build `release` est donc sans INTERNET.

**Panne.** `flutter build apk --release` (ou `appbundle`), installation sur un téléphone : l'écran de connexion s'affiche, l'utilisateur saisit ses identifiants, et `POST /api/auth/login` échoue immédiatement en `SocketException: Failed host lookup` (dio → `DioExceptionType.connectionError` → `ApiException.message` « erreur réseau »). Aucun écran ne peut charger la moindre donnée : l'app est entièrement inutilisable en release, alors qu'elle fonctionne parfaitement en `flutter run` (debug). Aucun job CI ne construit d'artefact Android, donc rien ne détecte la régression.

**Correction proposée.** Ajouter `<uses-permission android:name="android.permission.INTERNET"/>` dans `android/app/src/main/AndroidManifest.xml` (au niveau `<manifest>`, avant `<application>`), et ajouter au job `mobile` de la CI une étape `flutter build apk --release --debug-info=/dev/null` (ou au minimum `flutter build appbundle`) suivie d'une vérification `aapt2 dump permissions` / lecture du manifeste fusionné dans `build/app/intermediates/merged_manifests/release/AndroidManifest.xml`.

**Vérification adversariale.** Reconstitué de bout en bout. `android/app/src/main/AndroidManifest.xml` (lu intégralement) ne contient aucun `<uses-permission>` : uniquement `<application>` (label, MainActivity, deux intent-filters dont le deep link `coparentplanner://`) et un bloc `<queries>` PROCESS_TEXT. `android/app/src/debug/AndroidManifest.xml` et `android/app/src/profile/AndroidManifest.xml` déclarent bien `android.permission.INTERNET`, mais ces source sets ne sont fusionnés que pour les variantes debug/profile. Vérification des plugins Android résolus dans `.flutter-plugins-dependencies` (app_links 7.0.0, connectivity_plus 7.1.1, flutter_secure_storage 9.2.4, jni 1.0.0, jni_flutter 1.0.1, path_provider_android 2.3.1, sqlite3_flutter_libs 0.5.42) : j'ai lu leurs `android/src/main/AndroidManifest.xml` dans le pub-cache — seul connectivity_plus déclare une permission, `ACCESS_NETWORK_STATE` ; aucun ne déclare INTERNET (path_provider_android n'a même pas de manifeste). L'embedding Flutter release n'en déclare pas non plus, c'est précisément la raison d'être des manifestes debug/profile du template. Le manifeste fusionné d'une build release est donc sans INTERNET : tout appel dio échoue en `SocketException` → `DioExceptionType.connectionError`, et l'app est inerte dès l'écran de connexion. Aucun job CI ne construit d'artefact Android (`.github/workflows/ci.yml` job `mobile` = analyze/test ; le seul build packagé est iOS, Lot 9), donc rien ne détecte la régression.

**Rectification du vérificateur.** Gravité ramenée de P0 à P1 : ce n'est ni une faille de sécurité, ni une perte de données, ni un crash — l'app démarre et s'affiche, seules les requêtes réseau échouent. Et aucun artefact Android release n'est produit aujourd'hui (ni en CI, ni livré), donc l'impact est différé au premier build de distribution. Le défaut lui-même est réel et total sur cet artefact : tous les parcours sont cassés.

### C18 — Collision de préfixe « /api/me » ⊃ « /api/memberships » : modification et retrait d'un membre cassés

**Gravité** : P1 · **Axe** : reseau-repos · **Emplacement** : `mobile/lib/core/network/interceptors/api_routes.dart:13`
· **Contrat** : CLAUDE.md — invariant « Scope famille obligatoire » ; cdc §3.6 ; Lot 1 US-MBR-2/3/4/5.

**Preuve.** ```dart
if (path.contains('/api/me')) return false; // ligne 13
```
En Dart, `'/api/memberships/3f2a…'.contains('/api/me')` vaut **`true`** : `/api/me` est un préfixe littéral de `/api/memberships`. Les routes `PATCH /api/memberships/{id}` et `DELETE /api/memberships/{id}` (déclarées dans `contracts/openapi.json`) sont donc classées « non scopées » et partent sans `X-Family-Id`.
Or `backend/src/State/Member/UpdateMembershipProcessor.php:56` et `RemoveMembershipProcessor.php:43` appellent tous deux `$this->scope->require()`, qui exige l'en-tête (`FamilyScope.php:59-62`, 400). Les appelants côté mobile sont `MembersRepository.updateMembership()` (members_repository.dart:35) et `removeMembership()` (members_repository.dart:52), tous deux documentés comme reposant sur l'intercepteur (members_repository.dart:10).
À noter que ce défaut est **indépendant** du précédent : corriger la ligne 14 sans corriger la ligne 13 laisse la gestion des membres cassée.

**Panne.** Un parent admin ouvre Réglages › Membres, change le rôle du co-parent de `child` à `parent` (ou décoche un droit, ou change la couleur, ou retire un membre). `MembersRepository.updateMembership()` émet `PATCH /api/memberships/<uuid>` sans `X-Family-Id` → 400 `/errors/family-scope-required`. L'écran affiche « Le header X-Family-Id est requis pour cette ressource. » (members_screen.dart:40). US-MBR-2/3/4/5 sont inaccessibles depuis le mobile, y compris le retrait d'un membre et l'auto-départ.

**Correction proposée.** Ne jamais tester l'appartenance d'un chemin par `contains`. Utiliser une comparaison de segments : `path == '/api/me' || path.startsWith('/api/me/')`. Ajouter un cas de test explicite `'/api/memberships/<uuid>' → scopé` dans `test/core/network/interceptors_test.dart`.

**Vérification adversariale.** Vérifié. `api_routes.dart:13` teste `path.contains('/api/me')`, et `/api/me` est un préfixe littéral de `/api/memberships` : `'/api/memberships/<uuid>'.contains('/api/me')` vaut `true` en Dart. Le client généré émet exactement ce chemin (`lib/api/generated/clients/member_client.g.dart:63` et `:86`, déclarés `@PATCH('/api/memberships/{id}')` / `@DELETE` dans member_client.dart:32/42), donc `PATCH`/`DELETE` partent sans `X-Family-Id`. Côté backend, `UpdateMembershipProcessor::process` et `RemoveMembershipProcessor::process` appellent `$this->scope->require()` en toute première instruction, qui exige l'en-tête (`FamilyScope.php:59-62` → 400 `/errors/family-scope-required`). Les appelants mobiles sont bien `MembersRepository.updateMembership()` / `removeMembership()`, sans en-tête manuel. Le test existant (`interceptors_test.dart:35-45`) ne teste que `/api/me` et `/api/auth/login`, donc ne détecte rien. Défaut indépendant du C17 : corriger la ligne 14 seule laisse la gestion des membres cassée.

**Rectification du vérificateur.** Le constat cite `api_routes.dart:13` pour la ligne fautive, c'est exact. Seule nuance : le changement de couleur par soi-même (self) est également bloqué, alors que le backend l'autorise sans droit `family_settings` (UpdateMembershipProcessor.php:65-70) — le 400 tombe avant, à `require()`.

### C9 — Les mutations en file d'un compte sont rejouées sous l'identité du compte suivant connecté sur l'appareil

**Gravité** : P1 · **Axe** : offline-sync · **Emplacement** : `mobile/lib/core/sync/outbox_service.dart:60`
· **Contrat** : specs/lots/lot-8-pwa-offline-rgpd.md §3.1 (clé d'idempotence « scopée à l'utilisateur et à la famille : aucune collision entre utilisateurs ») ; CLAUDE.md (scope famille validé contre les memberships de l'utilisateur)

**Preuve.** L'entrée outbox ne mémorise que `method`, `path`, `body`, `headers` (uniquement `X-Family-Id`, ligne 48-50), `idempotencyKey`, `createdAt`, `status` (outbox_entry.dart:11-25) : aucun identifiant d'utilisateur. `flush()` (outbox_service.dart:60-65) rejoue toutes les entrées `pending` sans filtre de compte, et le `Bearer` est posé au moment de l'envoi par `AuthInterceptor.onRequest` qui relit le jeton COURANT dans le stockage sécurisé (auth_interceptor.dart:41-46). Comme `logout()` (auth_controller.dart:108-112) ne vide pas la table outbox, les entrées de l'utilisateur A survivent à sa déconnexion. À la connexion de B, le shell remonte `OfflineBanner`, dont `initState` déclenche `flush()` (offline_banner.dart:26-28) : les requêtes de A partent avec le jeton de B et le `X-Family-Id` figé de A (family_scope_interceptor.dart:19-24).

**Panne.** Sur la tablette familiale, le parent A crée hors-ligne un événement « Rendez-vous 14h » (entrée outbox pending). A se déconnecte sans avoir retrouvé le réseau. Le parent B se connecte et le réseau revient : l'événement est créé côté serveur sous l'identité de B (auteur, `AuditLog`, notifications e-mail au « bon » parent — tout est faux). Si B n'est pas membre de la famille de A, le backend répond 403, l'entrée passe `rejected` (outbox_service.dart:102-112) et la saisie de A est détruite en silence, sans que A ni B n'en soient informés.

**Correction proposée.** Ajouter une colonne `userId` sur `OutboxEntries`, renseignée à l'`enqueue` ; ne rejouer dans `flush()` que les entrées de l'utilisateur courant, et purger (ou geler explicitement en signalant à l'utilisateur avant déconnexion) les entrées restantes lors du `logout()`/`forceLogout()`.

**Vérification adversariale.** Reconstitué en entier. `OutboxEntries` (lib/core/storage/drift/tables/outbox_entry.dart:11-24) ne porte AUCUN identifiant d'utilisateur : id, method, path, body, headers (X-Family-Id figé), idempotencyKey, createdAt, status, attempts, lastError. `OutboxService.flush()` (lib/core/sync/outbox_service.dart:60-65) rejoue toutes les entrées `pending` sans aucun filtre. Le Bearer est posé à l'envoi par `AuthInterceptor.onRequest` (lib/core/network/interceptors/auth_interceptor.dart:37-47) qui relit `_storage.readAccessToken()` COURANT, tandis que `FamilyScopeInterceptor` (lib/core/network/interceptors/family_scope_interceptor.dart:18-24) impose le `X-Family-Id` FIGÉ de l'entrée (extra['xFamilyId']). Côté déconnexion : `AuthController.logout()` (lib/features/auth/application/auth_controller.dart:108-112) et `forceLogout()` (115-119) n'appellent que `_repo.logout()`/`clearTokens()` + `familyContext.clear()` ; `AuthRepository.logout()` (lib/features/auth/data/auth_repository.dart:134-144) ne touche que le stockage sécurisé. Vérifié par grep : aucun appel à `outboxDao`, `deleteEntry`, `purgeSynced` ou à un wipe de la base Drift hors du service outbox lui-même — la table survit donc à la déconnexion. À la connexion suivante, `HomeShell` (lib/features/home/shell/home_shell.dart:36) monte `OfflineBanner` dont `initState` déclenche `flush()` (lib/core/widgets/offline_banner.dart:23-29). Le chemin exact est donc : mutation de A en file → logout A → login B → flush → requête de A envoyée avec le jeton de B. Si B est membre de la famille figée (cas normal du couple coparental sur un appareil partagé), la mutation est créée sous l'identité de B (auteur, AuditLog) ; sinon 403 → `rejected` terminal (outbox_service.dart:100-112) et la saisie de A disparaît, d'autant plus silencieusement qu'aucune UI n'expose l'état rejeté (cf. C10). Rien dans PROGRESS.md (§ journal 2026-07-10 Étape D/F, l.421-423) n'assume cette limitation.

**Rectification du vérificateur.** Deux précisions : (1) le déclencheur cité `offline_banner.dart:26-28` est bien le post-frame de `initState` (lignes 23-29 exactement) ; (2) le cas le plus grave n'est pas le 403 mais l'inverse — quand B EST membre de la même famille (situation courante), il n'y a aucun refus serveur : la mutation de A est acceptée et attribuée à B, sans trace du problème. La perte silencieuse (403) n'est que la variante « famille étrangère ».

### C7 — Une entrée outbox restée « inFlight » n'est jamais rejouée ni purgée : la mutation est perdue silencieusement si l'app est tuée pendant l'envoi

**Gravité** : P1 · **Axe** : offline-sync · **Emplacement** : `mobile/lib/core/sync/outbox_service.dart:68`
· **Contrat** : specs/lots/lot-8-pwa-offline-rgpd.md §3.1 (« Atomicité locale … crash/redémarrage laisse la file cohérente ») ; US-OFF-2 (« ne pas perdre ma saisie »)

**Preuve.** `_send()` fait `await _dao.updateStatus(entry.id, OutboxStatus.inFlight);` (outbox_service.dart:68) AVANT la requête HTTP, et seul le retour de `_dio.request` (ligne 83) ou le `catch (DioException)` (ligne 100) fait repasser l'entrée en `pending`/`synced`/`rejected`. **Gravité** : P1 · **Axe** : securite-auth · **Emplacement** : `mobile/lib/features/auth/application/auth_controller.dart:28`

**Panne.** Utilisateur connecté, mode avion, lancement à froid de l'app. `GET /api/me` échoue en `connectionError` → `ApiException(statusCode: null)` → `clearTokens()` → état `AuthUnauthenticated` → le routeur affiche `/login`. Persister un profil minimal (id/email/locale) pour pouvoir rehydrater. Contredit bien specs/lots/lot-8-pwa-offline-rgpd.md §US-OFF-1 (l. 148-158). Les tests existants ne couvrent que 401 (test/features/auth/auth_controller_test.dart:162-169) : aucun test n'exerce le cas réseau. **Preuve.** La balise `<application>` ne porte ni `android:allowBackup="false"`, ni `android:fullBackupContent`, ni `android:dataExtractionRules` : Android Auto Backup est donc actif par défaut et sauvegarde le répertoire de fichiers de l'app vers le compte Google de l'utilisateur. Android Auto Backup est donc actif par défaut. Les deux stockages visés sont bien concernés : la base Drift est ouverte dans `getApplicationSupportDirectory()` (mobile/lib/core/storage/drift/database.dart:44-49, fichier `coparentplanner.sqlite`, `NativeDatabase` non chiffré) — répertoire de fichiers de l'app, inclus par défaut dans la sauvegarde — et y stocke les payloads JSON bruts des endpoints métier (`CacheDao.put`, cache_dao.dart:17-27, alimenté pour `children`, `events`, `exchanges` via `ReadCache.list`, read_cache.dart:45-52). `FlutterSecureStorageAdapter` utilise `AndroidOptions(encryptedSharedPreferences: true)` (secure_storage.dart:28-30), dont le blob part en sauvegarde alors que la clé maître du Keystore, elle, non : la restauration sur un nouvel appareil laisse un blob indéchiffrable. Aucune trace de décision assumée dans PROGRESS.md (aucune occurrence de « backup »/« sauvegarde »).

**Rectification du vérificateur.** Détail de localisation : la balise `<application>` ouvre en ligne 2 (la ligne 3 citée est `android:label`) — le constat vise bien le bon élément. Le volet (b) est plausible mais son symptôme exact dépend du plugin : selon que `flutter_secure_storage` lève ou renvoie null à la lecture, on obtient soit une exception non `ApiException` remontant depuis `restoreSession()` (main.dart:22, avant `runApp`), soit un simple retour à l'écran de connexion ; seul le volet (a), confidentialité, est certain.

### C8 — Le cache de lecture Drift n'est cloisonné que par famille, jamais par utilisateur, et n'est purgé ni à la déconnexion ni à la suppression de compte

**Gravité** : P2 (annoncée P1) · **Axe** : offline-sync · **Emplacement** : `mobile/lib/core/storage/drift/daos/cache_dao.dart:14`
· **Contrat** : specs/lots/lot-8-pwa-offline-rgpd.md US-OFF-1 (« le cache est cloisonné … jamais de fuite ») et US-PWA-3 (« l'offline n'ouvre aucune porte d'autorisation, §7 ») ; CLAUDE.md (scope famille + autorisation par Voters vérifiée sur chaque ressource)

**Preuve.** La clé de cache est `static String keyFor(String familyId, String endpoint) => '$familyId::$endpoint';` (cache_dao.dart:14-15) : aucune composante utilisateur. `AuthController.logout()` (auth_controller.dart:108-112) ne fait que `_repo.logout()` + `familyContextProvider.clear()` ; `forceLogout()` (ligne 116-120) idem ; `PrivacyScreen._deleteAccount()` (privacy_screen.dart:71-73) appelle `deleteAccount()` puis `forceLogout()`. Aucun de ces chemins ne touche la base Drift. `CacheDao.purgeFamily()` (cache_dao.dart:34-38) existe mais n'est appelée NULLE PART dans `lib/` (vérifié par grep sur tout le dépôt : seule la définition apparaît). Le fichier `coparentplanner.sqlite` (database.dart:44-49) n'est pas chiffré et conserve donc en clair les payloads JSON des endpoints `children`, `events` et `exchanges`. Or l'accès à ces endpoints est contrôlé par droit côté serveur (`backend/src/State/Child/ChildrenProvider.php:16` : « droit `children_notes ≥ view` »), alors que le repli cache de `ReadCache.list` (read_cache.dart:58-67) ne vérifie aucun droit.

**Panne.** Tablette familiale partagée. Le parent A (droit `children_notes: edit`) consulte l'onglet Enfants en ligne : la fiche des enfants est mise en cache sous la clé `F::children`. A se déconnecte. Le beau-parent B, membre de la même famille F mais avec `children_notes: none`, se connecte et sélectionne F. En ligne, l'API lui renvoie 403 et l'écran reste vide. Il passe en mode avion, rouvre l'onglet Enfants : `ReadCache` sert le payload mis en cache par A — B lit des données auxquelles il n'a aucun droit. Variante RGPD : après `DELETE /api/me` (droit à l'effacement), toutes les données de famille de l'utilisateur restent en clair dans le SQLite de l'appareil, indéfiniment (aucune purge, aucun TTL — `cachedAt` est écrit mais jamais relu).

**Correction proposée.** (1) Purger le stockage local à toute fin de session : appeler `cacheDao.purgeAll()` + suppression des entrées outbox dans `AuthController.logout()`, `forceLogout()` et après `deleteAccount()`. (2) Inclure l'identifiant utilisateur dans la clé de cloisonnement (`keyFor(userId, familyId, endpoint)` + colonne `userId` sur `CacheEntries`), pour qu'un cache ne puisse jamais être servi à un autre compte même sans purge. (3) Appliquer un TTL sur `cachedAt` (l'attribut est déjà stocké) pour ne pas servir un instantané de droits arbitrairement ancien.

**Vérification adversariale.** Les deux faits matériels sont exacts. La clé de cache ne porte aucune composante utilisateur : `keyFor(String familyId, String endpoint) => '$familyId::$endpoint'` (cache_dao.dart:14-15). Et aucune fin de session ne purge la base locale : `logout()` (auth_controller.dart:108-112) et `forceLogout()` (l.116-120) ne font que `_repo.logout()`/`clearTokens()` + `familyContextProvider.clear()` ; `PrivacyScreen._deleteAccount()` (privacy_screen.dart:71-74) enchaîne `deleteAccount()` puis `forceLogout()` ; `CacheDao.purgeFamily()` (cache_dao.dart:34-38) n'est appelée nulle part dans `lib/` (grep : seule la définition, plus un usage nul de `purgeSynced()` hors test). Le chemin de fuite est reconstituable : `familyChildrenProvider` → `ChildrenRepository.listChildren()` (children_repository.dart:18-28) → `ReadCache.list()` qui, sur `DioException` sans réponse HTTP (hors-ligne), sert le payload stocké sous `F::children` sans aucune vérification de droit (read_cache.dart:54-68), alors que côté serveur la lecture exige `children_notes ≥ view` (backend/src/State/Child/ChildrenProvider.php:16). Un second compte membre de la même famille, sur le même appareil et hors-ligne, lit donc des données que l'API lui refuse en ligne. Rien de tout cela n'est documenté comme assumé dans PROGRESS.md (§ Lot 8 ne mentionne que le cloisonnement famille).

**Rectification du vérificateur.** La référence spec est en partie mal choisie : US-PWA-3 « l'offline n'ouvre aucune porte d'autorisation » (specs/lots/lot-8-pwa-offline-rgpd.md:127-130) porte sur le refus 403 d'une MUTATION côté web, et US-OFF-1 (l.160-162) n'exige explicitement qu'un cloisonnement par `family_id` — aucune spec ne prescrit un cloisonnement par utilisateur. Le constat tient donc sur l'invariant d'autorisation de CLAUDE.md et sur l'absence de purge, pas sur une exigence littérale du lot 8. Gravité ramenée à P2 : le volet certain et testable est l'absence de purge à la déconnexion / après `DELETE /api/me` ; le volet fuite inter-comptes est réel mais conditionné à un appareil partagé, deux comptes de la même famille aux droits différents et un passage hors-ligne.

### C12 — `flush()` n'a ni garde de connectivité ni verrou d'exécution : deux flushs concurrents envoient la même entrée et le 409 « in_progress » du serveur est interprété comme un refus définitif

**Gravité** : P2 · **Axe** : offline-sync · **Emplacement** : `mobile/lib/core/sync/outbox_service.dart:60`
· **Contrat** : specs/lots/lot-8-pwa-offline-rgpd.md §3.1 (flushOutbox étape 1 ; traitement séquentiel FIFO) et §3.2

**Preuve.** `flush()` (outbox_service.dart:60-65) lit `pendingEntries()` puis boucle, sans verrou ni drapeau d'exécution, et sans le garde-fou §3.1 « 1. si pas de réseau → return ». Deux déclencheurs peuvent se chevaucher : le post-frame de `OfflineBanner.initState` (offline_banner.dart:26-28) et le `ref.listen(connectivityProvider, …) { unawaited(service.flush()); }` du provider (outbox_service.dart:146-150). Le README de `connectivity_plus 7.1.1` avertit que le flux « can give multiple or unreliable results. For example, reporting connectivity "none" followed by connectivity "wifi" right after reconnecting » et « doesn't filter events, nor it ensures distinct values » : chaque émission non-`none` relance donc un flush. Comme le passage à `inFlight` n'a lieu qu'après le premier `await` de `_send`, un second `pendingEntries()` peut renvoyer la même entrée. Côté serveur, deux requêtes concurrentes portant la même clé donnent un 409 : `IdempotencySubscriber` (backend/src/EventSubscriber/IdempotencySubscriber.php:110-115) lève `IdempotencyConflictException` quand l'entrée est `in_progress` et récente. Or le client classe 409 comme refus TERMINAL (outbox_service.dart:102-112, `_reason` → 'conflict').

**Panne.** Retour du réseau après une coupure : le shell se remonte et la connectivité émet coup sur coup « none » puis « wifi » (comportement iOS documenté). Deux flushs partent, la même création d'événement est postée deux fois. La première aboutit (événement créé, 201) ; la seconde reçoit 409 « in_progress ». L'entrée est marquée `rejected` — un refus définitif — alors que la mutation a en réalité réussi ; comme aucune UI n'expose l'état rejeté, l'utilisateur ne voit qu'un compteur qui retombe à 0, et un éventuel `retry()` manuel rejouerait une clé désormais `completed`.

**Correction proposée.** Rendre `flush()` single-flight (un `Future<void>? _running` réutilisé ou un mutex), et ne rien tenter si `connectivityProvider` est faux (§3.1 étape 1). Marquer l'entrée `inFlight` en transaction Drift conditionnelle (`UPDATE … WHERE id = ? AND status = pending`) et n'envoyer que si la ligne a bien été prise. Ne traiter comme terminal qu'un 409 métier, et distinguer le 409 d'idempotence concurrente (le backend peut le signaler par un type RFC 7807 dédié) pour le laisser en `pending`.

**Vérification adversariale.** Les deux manques sont réels : `flush()` (lib/core/sync/outbox_service.dart:60-65) n'a ni drapeau d'exécution ni mutex, et ne contrôle pas la connectivité alors que la spec l'impose en étape 1 (specs/lots/lot-8-pwa-offline-rgpd.md, `flushOutbox` : « 1. si pas de réseau → return »). Le passage à `inFlight` n'intervient qu'au premier `await` de `_send` (l.68), après le `pendingEntries()` de l'appelant : deux flushs qui se chevauchent peuvent sélectionner la même entrée. Et le classement du 409 est bien terminal (l.100-112, `_reason` → 'conflict', l.132). Côté serveur, `IdempotencySubscriber::onRequest` (backend/src/EventSubscriber/IdempotencySubscriber.php:104-113) lève bien `IdempotencyConflictException` (409) quand une entrée `in_progress` a moins de 300 s. La conséquence — une mutation en réalité aboutie marquée `rejected` définitivement — est donc atteignable.

**Rectification du vérificateur.** Deux corrections. (1) Le déclencheur cité (deux flushs concurrents via double émission de `connectivity_plus`) est le chemin le PLUS étroit : `ref.listen` (outbox_service.dart:146-150) ne tire pas à la souscription et le passage « none → wifi » ne produit qu'un seul flush ; il faut deux émissions non-`none` rapprochées. Le chemin le plus directement atteignable pour la MÊME panne est le `RetryInterceptor` (lib/core/network/interceptors/retry_interceptor.dart:44-64), qui rejoue une requête portant déjà l'`Idempotency-Key` 300 ms après un `connectionError`/`receiveTimeout` : si le serveur traite encore la première, la seconde reçoit le 409 `in_progress` et l'entrée est marquée `rejected` terminal. (2) La panne annoncée est fausse sur un point : il n'y a PAS de doublon côté serveur — c'est précisément l'idempotence qui renvoie le 409 (ou rejoue la réponse mémorisée si la première est déjà `completed`, IdempotencySubscriber.php:92-99). Le dommage se limite à une entrée faussement `rejected` (invisible, cf. C10), sauf si la première requête a été interrompue avant commit : la mutation est alors perdue sans notification. D'où P2 et non P1.

### C3 — Le cache de lecture local n'est purgé ni à la déconnexion ni à la suppression de compte, et n'est cloisonné que par famille

**Gravité** : P2 (annoncée P1) · **Axe** : securite-auth · **Emplacement** : `mobile/lib/core/sync/read_cache.dart:59`
· **Contrat** : CLAUDE.md (autorisation vérifiée sur chaque ressource) ; specs/lots/lot-8-pwa-offline-rgpd.md §7 point 2 ; specs/cdc.md §7 (droit à l'effacement)

**Preuve.** Le repli hors-ligne lit `_dao.get(familyId, endpoint)` : la clé est `"$familyId::$endpoint"` (mobile/lib/core/storage/drift/daos/cache_dao.dart:14) — cloisonnée par famille mais **pas par utilisateur ni par droits**. `CacheDao.purgeFamily` (cache_dao.dart:34), dont le commentaire annonce « purge par famille (ex. à la déconnexion / suppression de compte) », n'est appelé nulle part : `grep -rn "purgeFamily" lib/` ne renvoie que sa déclaration. `AuthController.logout()`/`forceLogout()` (auth_controller.dart:108-120) ne touchent pas Drift, et `PrivacyScreen._deleteAccount` (mobile/lib/features/settings/presentation/privacy_screen.dart:71-73) fait `deleteAccount()` puis `forceLogout()` sans rien effacer localement. **Panne.** (a) Fuite inter-comptes : un parent consulte les fiches enfants et le fil d'échanges sur la tablette familiale, puis se déconnecte. L'ado, membre `child` de la même famille avec `children_notes = none`, se connecte sur la même tablette et passe hors-ligne : `ChildrenScreen` et `ExchangesScreen` servent depuis le cache les fiches et messages mis en cache par le parent — la vérification de droits, qui n'existe que côté serveur, est court-circuitée. (b) RGPD : après `DELETE /api/me` (droit à l'effacement), toutes les données de la famille restent en clair dans le SQLite local de l'appareil, indéfiniment.

**Correction proposée.** Appeler la purge locale (`CacheDao` + outbox) depuis `logout()`, `forceLogout()` et après `deleteAccount()` — le plus simple étant un `LocalDataWiper` qui vide les deux tables Drift. Et inclure l'identité dans la clé de cache (`"$userId::$familyId::$endpoint"`, avec `userId` disponible via `AuthAuthenticated.user.id`) pour qu'un changement de compte ne puisse structurellement pas relire les données de l'autre.

**Vérification adversariale.** Faits vérifiés : `CacheDao.purgeFamily` (mobile/lib/core/storage/drift/daos/cache_dao.dart:34-38) est bien du code mort — un grep sur tout `lib/` et `test/` ne renvoie que sa déclaration ; ni `logout()`/`forceLogout()` (auth_controller.dart:107-119) ni `PrivacyScreen._deleteAccount` (mobile/lib/features/settings/presentation/privacy_screen.dart:70-74, `deleteAccount()` puis `forceLogout()`) n'effacent quoi que ce soit en local. Le contenu du cache est bien personnel et en clair : `ChildrenRepository.listChildren` (children_repository.dart:19-27) et `ExchangesRepository.list` (exchanges_repository.dart:29-38) passent par `ReadCache.list`, qui écrit `jsonEncode(items.map(toJson))` dans `cache_entries` (read_cache.dart:48-52) d'une base SQLite non chiffrée (`NativeDatabase.createInBackground(file)`, mobile/lib/core/storage/drift/database.dart:43-50). Le rôle `child` existe bien côté mobile (lib/features/members/presentation/invite_screen.dart:99-115, agenda_screen.dart:729), donc un second compte de la même famille aux droits réduits peut se connecter sur le même appareil et, hors-ligne, se voir servir depuis le cache les fiches enfants et les échanges chargés par le parent (read_cache.dart:59-66) — la vérification de droits n'existant que côté serveur. Le volet (b) est incontestable : après `DELETE /api/me`, toutes les données restent indéfiniment en clair dans `coparentplanner.sqlite`.

**Rectification du vérificateur.** Deux nuances. (1) Le cloisonnement par famille seul n'est PAS un écart à la spec : specs/lots/lot-8-pwa-offline-rgpd.md §7 point 1 n'exige que « caches PWA et Drift cloisonnés par famille » — ajouter l'`userId` à la clé est une amélioration, pas la correction d'une violation. Le défaut réellement démontrable est l'absence totale d'appel à la purge locale à la déconnexion et après suppression de compte. (2) Gravité ramenée à P2 : le scénario de fuite inter-comptes exige la conjonction d'un appareil partagé, d'un second membre de la MÊME famille aux droits réduits et d'un passage hors-ligne ; la rétention post-effacement, elle, est certaine mais purement locale à l'appareil.

### C13 — Un timeout après traitement serveur enfile une nouvelle requête avec une Idempotency-Key différente : l'événement est créé deux fois

**Gravité** : P2 · **Axe** : offline-sync · **Emplacement** : `mobile/lib/features/agenda/data/agenda_repository.dart:69`
· **Contrat** : specs/lots/lot-8-pwa-offline-rgpd.md §3.1 (note « l'outbox est l'unique chemin de mutation côté mobile » ; « Idempotency-Key immuable pour la durée de vie de l'entrée ») ; US-OFF-2 scénario « rejeu idempotent (doublon réseau) »

**Preuve.** `createEvent` envoie d'abord la requête en direct via le client généré (agenda_repository.dart:65-68), donc SANS `Idempotency-Key` : `IdempotencyInterceptor` ne pose l'en-tête que si `options.extra['idempotencyKey']` est présent (idempotency_interceptor.dart:9-14), ce que seul le chemin outbox renseigne (outbox_service.dart:76-80). Le repli hors-ligne est déclenché par `on DioException catch (e) { if (e.response != null) … ; await _outbox.enqueue(...) }` (lignes 69-81), c'est-à-dire pour TOUTE `DioException` sans réponse HTTP — ce qui inclut `receiveTimeout` (20 s, network_providers.dart:88) et `connectionError` survenant après que le serveur a déjà traité la requête. `enqueue` génère alors une clé neuve (`idempotencyKey: _uuid.v4()`, outbox_service.dart:51), que le serveur voit comme une requête inédite. La spec prévoit précisément l'inverse : « l'outbox est l'unique chemin de mutation côté mobile → cohérence garantie online/offline » et « Un rejeu (timeout puis retry) renvoie la même clé → le serveur dédoublonne ».

**Panne.** Réseau 3G instable. L'utilisateur valide la création d'un événement ; le POST atteint le serveur, l'événement est créé et publié sur Mercure, mais la réponse se perd et Dio lève un `receiveTimeout` au bout de 20 s. L'app enfile la même création avec une nouvelle clé et affiche « en attente de synchro ». Au flush suivant, un second événement identique est créé : l'agenda de la famille contient deux « Sortie scolaire 8h », et l'autre parent reçoit deux notifications.

**Correction proposée.** Faire passer toute mutation par l'outbox (générer la clé et persister l'entrée AVANT l'envoi, puis flusher immédiatement si en ligne), conformément à §3.1 ; à défaut, générer l'`Idempotency-Key` dans `createEvent` et la transmettre à la fois à la requête directe (via `extra`) et à `enqueue`, pour que le rejeu réutilise la clé du premier essai.

**Vérification adversariale.** Chemin reconstitué de bout en bout. `AgendaRepository.createEvent` envoie le POST directement par le client généré (mobile/lib/features/agenda/data/agenda_repository.dart:65-68) : aucune `extra['idempotencyKey']` n'est posée, or `IdempotencyInterceptor.onRequest` ne pose l'en-tête que si cette extra est présente (mobile/lib/core/network/interceptors/idempotency_interceptor.dart:9-14). Le `catch` de repli s'applique à toute `DioException` sans réponse HTTP (agenda_repository.dart:69-81), donc à `receiveTimeout` (20 s, mobile/lib/core/network/network_providers.dart:19) et `connectionError`, y compris quand le serveur a déjà traité la requête. `OutboxService.enqueue` génère alors une clé neuve (`idempotencyKey: _uuid.v4()`, mobile/lib/core/sync/outbox_service.dart:51) et `_send` l'envoie telle quelle (outbox_service.dart:76-80). Côté serveur, la déduplication dépend exclusivement de l'en-tête : `CreateEventProcessor::process` lit `Idempotency-Key` et bascule sur `createSimple()` (donc création inconditionnelle) quand la clé est absente (backend/src/State/Agenda/CreateEventProcessor.php:54-56, 69-82) ; `IdempotencySubscriber` ne s'arme lui aussi que sur présence de l'en-tête. Aucune autre garde n'intercepte le cas : `RetryInterceptor` refuse précisément de rejouer un POST sans `Idempotency-Key` (mobile/lib/core/network/interceptors/retry_interceptor.dart:33-36), ce qui montre que le rejeu du POST keyless est reconnu comme dangereux — mais le repli outbox contourne cette garde en réémettant la mutation avec une clé différente. Aucun test ne couvre ce chemin et PROGRESS.md ne documente pas cette limitation (§ Lot 8 étape D dit au contraire « createEvent routé vers l'outbox hors-ligne »). Résultat observable : deux événements identiques dans l'agenda familial, double notification e-mail à l'autre parent.

**Rectification du vérificateur.** Deux précisions : (1) la panne exige la fenêtre étroite « serveur a traité, réponse perdue » — hors de cette fenêtre le repli outbox est correct ; c'est bien un P2, pas davantage. (2) Le constat vaut au-delà de l'agenda par construction, mais seul `createEvent` est câblé sur l'outbox aujourd'hui (les autres écrans ne passent pas du tout par la file — polish documenté PROGRESS.md:421-423), donc le défaut se limite pour l'instant à ce seul appel.

### C11 — Aucun effet optimiste local : l'entité créée hors-ligne n'apparaît sur aucun écran, ce qui pousse l'utilisateur à la ressaisir (doublons à la resynchro)

**Gravité** : P2 (annoncée P1) · **Axe** : offline-sync · **Emplacement** : `mobile/lib/features/agenda/data/agenda_repository.dart:76`
· **Contrat** : specs/lots/lot-8-pwa-offline-rgpd.md §3.1 (enqueueMutation, étapes 2 et 4) ; US-OFF-2 scénario nominal

**Preuve.** Le chemin hors-ligne de `createEvent` se limite à `await _outbox.enqueue(...)` puis `throw const OutboxQueuedException();` (agenda_repository.dart:76-82) : rien n'est écrit dans le cache de lecture. `OutboxService.enqueue` (outbox_service.dart:35-57) n'insère que la ligne outbox. Côté lecture, `listEvents` repart de `ReadCache.list` qui, hors-ligne, renvoie tel quel le dernier payload serveur (`read_cache.dart:59-67`) — sans la création locale. L'écran ne rafraîchit d'ailleurs même pas la liste sur ce chemin : `ref.invalidate(familyEventsProvider)` n'est appelé que dans la branche succès (agenda_screen.dart:709), pas dans le `on OutboxQueuedException` (ligne 712-716). La spec impose l'étape manquante : « 2. appliquer l'effet OPTIMISTE dans le cache Drift (créer/màj l'entité avec un flag pending) » et « l'UI affiche optimistically l'entité avec un badge « En attente de synchro » ».

**Panne.** Dans le train (hors réseau), l'utilisateur crée l'événement « Sortie scolaire 8h ». Un SnackBar « en attente de synchro » apparaît puis disparaît, l'agenda du mois reste strictement identique : l'événement n'est visible nulle part. Convaincu que la saisie a échoué, l'utilisateur la refait — deux entrées outbox, deux `Idempotency-Key` distinctes. Au retour du réseau, deux événements identiques sont créés côté serveur et poussés en temps réel à l'autre parent.

**Correction proposée.** Dans le chemin outbox, écrire l'entité optimiste dans le cache Drift de l'endpoint concerné (même transaction que l'insertion outbox, cf. §3.1 « atomicité locale »), avec un marqueur `pending` exploité par l'UI pour le badge ; invalider le provider de lecture après enfilement, et remplacer/retirer l'optimiste à la transition `synced` (état canonique du corps de réponse) ou `rejected` (rollback).

**Vérification adversariale.** Le code cité dit bien ce qui est affirmé. `AgendaRepository.createEvent` (lib/features/agenda/data/agenda_repository.dart:69-82) : en cas d'erreur sans réponse (hors-ligne), il fait `await _outbox.enqueue(...)` puis `throw const OutboxQueuedException()` — rien d'autre. `OutboxService.enqueue` (outbox_service.dart:35-57) n'écrit QUE la ligne outbox, aucun accès au `CacheDao`. La lecture (`listEvents`, agenda_repository.dart:25-35) passe par `ReadCache.list` qui, hors-ligne, restitue le dernier payload serveur : la création locale n'y figure pas. Et le handler de l'écran (lib/features/agenda/presentation/agenda_screen.dart:712-716) ne fait que `pop()` + SnackBar, sans `ref.invalidate(familyEventsProvider)` (présent uniquement en branche succès, l.709). La spec impose l'étape absente : `enqueueMutation` étape 2 « appliquer l'effet OPTIMISTE dans le cache Drift (créer/màj l'entité avec un flag pending) » et étape 4 (badge), US-OFF-2 l.170. C'est donc un écart net et vérifiable à la spec, avec effet observable : l'événement créé hors-ligne n'apparaît sur aucun écran jusqu'à la resynchro.

**Rectification du vérificateur.** Gravité ramenée de P1 à P2 : le scénario de doublon est surestimé. L'utilisateur n'est pas sans retour — le SnackBar `offlineQueued` (« Enregistré — en attente de synchro », lib/l10n/app_fr.arb:294) s'affiche ET la bannière globale reste visible avec « 1 modification en attente de synchro » (`syncPending`, offline_banner.dart:44-50) tant que l'entrée est pending. La ressaisie en doublon reste possible mais n'est plus la conséquence probable ; le défaut réel et certain est l'absence d'affichage optimiste exigé par §3.1 étape 2 / US-OFF-2, pas une perte ni un doublon systématique.

### C5 — La réinitialisation de mot de passe ne purge pas les jetons locaux : la session se rouvre seule après un « révoquer toutes les sessions »

**Gravité** : P2 · **Axe** : securite-auth · **Emplacement** : `mobile/lib/features/auth/application/auth_controller.dart:88`
· **Contrat** : specs/lots/lot-0-fondations.md US-AUTH-2 sc.9 (le reset révoque les sessions)

**Preuve.** `resetPassword()` (l. 83-89) appelle `_repo.resetPassword(...)` puis fait seulement `state = const AuthUnauthenticated();` — jamais `_repo.clearTokens()` (idem `verifyEmail()`, l. 73-76). Côté serveur, `ResetPasswordProcessor` (backend/src/State/Auth/ResetPasswordProcessor.php:55) fait `revokeAllForUser($user)` : les refresh sont révoqués, mais un JWT d'accès déjà émis reste valide jusqu'à `ACCESS_TOKEN_TTL=900` (backend/.env:41) — il est impossible de le révoquer, le firewall `api` étant `stateless` (backend/config/packages/security.yaml). L'access token reste donc dans le Keychain/Keystore alors que le commentaire du code affirme « re-login requis ».

**Panne.** Session ouverte sur le téléphone, l'utilisateur ouvre le deep link `coparentplanner://reset-password?token=…` et change son mot de passe. L'app le renvoie sur `/login`. Il tue l'app et la relance dans les 15 minutes : `restoreSession()` voit `hasAccessToken() == true`, `GET /api/me` réussit avec l'ancien JWT → `AuthAuthenticated` : la session se rouvre sans aucune saisie du nouveau mot de passe, juste après une opération dont la finalité est de couper toutes les sessions. Effet de bord vérifiable du même jeton résiduel : sur l'écran de connexion, une faute de frappe renvoie 401 ; dans `AuthInterceptor.onError` (mobile/lib/core/network/interceptors/auth_interceptor.dart:64-72) l'en-tête utilisé est `null` alors que le stockage contient encore un jeton, la condition `'Bearer $current' != usedAuth` est vraie et `_replay` **renvoie la requête de connexion** — la tentative ratée est comptée deux fois par le rate-limiter (`$limiter->consume(1)`, backend/src/State/Auth/LoginProcessor.php:62-67), donc verrouillage deux fois plus rapide.

**Correction proposée.** Dans `resetPassword()` et `verifyEmail()`, appeler `await _repo.clearTokens()` (plus la purge du contexte famille et des données locales) avant de passer à `AuthUnauthenticated`. Indépendamment, court-circuiter les routes publiques dans l'intercepteur : en tête de `AuthInterceptor.onError`, ajouter `ApiRoutes.isAuthRoute(options.path)` à la condition de sortie (l. 58-62) — un 401 de `/api/auth/*` ne doit ni déclencher de refresh, ni de `forceLogout`, ni de rejeu.

**Vérification adversariale.** Chemin reconstitué de bout en bout. `ResetPasswordScreen._submit()` (mobile/lib/features/auth/presentation/reset_password_screen.dart:53-61) appelle `AuthController.resetPassword()` (auth_controller.dart:83-89) qui fait `await _repo.resetPassword(...)` puis `state = const AuthUnauthenticated();` — aucun `clearTokens()`, contrairement à `restoreSession()` (l.30) et `forceLogout()` (l.117) qui, eux, purgent. `AuthRepository.resetPassword()` (auth_repository.dart:119-131) ne touche pas non plus au stockage (seul `logout()` appelle `_storage.clearTokens()`). Les jetons restent donc dans le secure storage. Au redémarrage, `main()` (main.dart:22) appelle `restoreSession()` : `hasAccessToken()` renvoie vrai (auth_repository.dart:19-20), `GET /api/me` passe avec l'ancien JWT — firewall `api` `stateless: true` (backend/config/packages/security.yaml:22), `ACCESS_TOKEN_TTL=900` (backend/.env:41), et `ResetPasswordProcessor` ne révoque que les refresh (backend/src/State/Auth/ResetPasswordProcessor.php:55) → `AuthAuthenticated` sans saisie du nouveau mot de passe pendant ≤15 min. L'effet de bord sur le rate-limiter est également reconstituable : `AuthInterceptor.onRequest` n'attache pas de Bearer sur `/api/auth/*` (auth_interceptor.dart:41-46) donc `usedAuth == null` (l.64) ; `LoginProcessor` renvoie 401 sur mauvais mot de passe (`InvalidCredentialsException`, backend/src/Security/Auth/Exception/InvalidCredentialsException.php:12) après `$limiter->consume(1)` (LoginProcessor.php:62-64) ; la sortie anticipée l.58-62 ne filtre pas les routes d'auth, et le jeton résiduel non vide rend `'Bearer $current' != null` vrai (l.68-70) → `_replay()` (l.90-104) re-poste `/api/auth/login` avec le même corps, soit deux consommations du limiteur par tentative. `RetryInterceptor` ne rejoue pas les 401 (retry_interceptor.dart:26-36), donc le doublon vient bien de l'AuthInterceptor. Aucun test ne couvre ce chemin (test/core/network/interceptors_test.dart ne teste que le 401 sur route protégée), et PROGRESS.md ne documente pas cette limitation.

**Rectification du vérificateur.** Deux nuances. (1) La mention de `verifyEmail()` (l.73-76) est inopérante : on n'y arrive que depuis l'état `AuthPendingVerification`, où aucun jeton n'a jamais été écrit (`register()` n'en délivre pas, D1) — le seul chemin réellement fautif est `resetPassword()`. (2) La fenêtre est bornée : le refresh étant révoqué serveur-side, dès l'expiration de l'access token (≤900 s) l'intercepteur échoue au refresh et déclenche `forceLogout()` (auth_interceptor.dart:81-85). La session ré-ouverte est donc silencieuse mais éphémère, ce qui justifie P2 et non P1.

### C20 — Accueil « À venir » : la date d'un événement est calculée en UTC alors que l'API renvoie un offset — jour et jour de semaine faux

**Gravité** : P2 · **Axe** : reseau-repos · **Emplacement** : `mobile/lib/features/home/shell/home_tab.dart:493`
· **Contrat** : CLAUDE.md — « Fuseau par défaut Europe/Paris » ; cdc §6.1 (startsAt/endsAt formatés en ISO 8601 avec offset du fuseau famille).

**Preuve.** L'API sérialise `startsAt` en ISO 8601 **avec l'offset du fuseau famille** (`backend/src/Dto/Agenda/EventResource.php` docblock ; `OverlayEventResource.php:38` : `->setTimezone($tz)->format(\DateTimeInterface::ATOM)`), par ex. `2026-06-23T01:00:00+02:00`.
La carte « À venir » mélange deux modes de lecture incompatibles :
```dart
final start = DateTime.parse(event.startsAt);            // ligne 493 -> DateTime UTC (isUtc == true)
final meta  = event.allDay ? ... : event.startsAt.substring(11, 16); // ligne 497 -> heure locale famille, en texte
...
Text(_frenchShortDow(start).toUpperCase())               // ligne 513 -> weekday UTC
Text('${start.day}')                                     // ligne 522 -> jour du mois UTC
```
En Dart, `DateTime.parse` d'une chaîne portant un offset renvoie un `DateTime` **normalisé en UTC** ; ni `.toLocal()` ni décalage manuel ne sont appliqués. `start.day` / `start.weekday` sont donc ceux de l'instant UTC, pas ceux du fuseau famille. Les autres écrans évitent le piège en découpant la chaîne (`agenda_screen.dart:137/142/305/386` utilisent `substring`), ce qui confirme que le fuseau attendu est celui porté par la chaîne.

**Panne.** Famille en `Europe/Paris` (UTC+2 l'été, cdc « fuseau par défaut Europe/Paris »). Un événement « Départ aéroport » le mardi 23/06/2026 à 01:00 est renvoyé comme `2026-06-23T01:00:00+02:00`. `DateTime.parse` donne `2026-06-22 23:00Z`. La carte d'accueil affiche « MAR »→**« LUN »** et le chiffre **22**, tout en affichant l'heure « 01:00 » juste à côté : l'utilisateur lit « LUN 22 · 01:00 » pour un événement du mardi 23. Le même décalage frappe tout événement entre 00:00 et 02:00 heure de Paris (00:00–01:00 en hiver), et s'inverserait pour un fuseau famille à offset négatif.

**Correction proposée.** Ne jamais dériver une date civile d'un `DateTime.parse` sur une chaîne à offset. Soit découper la chaîne comme le fait `agenda_screen` (`startsAt.substring(0, 10)` puis `DateTime.parse` de la date seule, qui reste locale/naïve), soit centraliser un utilitaire `familyLocalDateTime(String iso)` qui reconstruit la date civile à partir des composants textuels de la chaîne. Ajouter un test avec `startsAt = '2026-06-23T01:00:00+02:00'` vérifiant que la carte affiche « MAR 23 ».

**Vérification adversariale.** Reconstitué. Le backend formate bien avec l'offset du fuseau famille : `backend/src/Dto/Agenda/EventResource.php:92` `$o->startsAt->setTimezone($tz)->format(\DateTimeInterface::ATOM)`. Côté mobile, `home_tab.dart:493` fait `DateTime.parse(event.startsAt)` — en Dart une chaîne portant un offset est normalisée en UTC (isUtc == true), sans `.toLocal()` — puis `:513` `_frenchShortDow(start)` (qui lit `d.weekday`, home_tab.dart:604-605) et `:522` `'${start.day}'`, tandis que la ligne 497 affiche l'heure par `startsAt.substring(11, 16)`, c'est-à-dire l'heure du fuseau famille. Pour `2026-06-23T01:00:00+02:00` : instant UTC `2026-06-22 23:00Z` → `weekday` = lundi, `day` = 22, en regard de « 01:00 » — la carte affiche « LUN 22 · 01:00 » pour un événement du mardi 23. Aucun test ne couvre le cas : `test/widgets/home_screens_test.dart:75-102` construit `startsAt` à partir de `DateTime.now()` et n'assertionne que le titre et la présence de la carte. Les autres écrans découpent la chaîne (`agenda_screen.dart`), ce qui confirme la convention attendue.

**Rectification du vérificateur.** Le filtre « à venir » de la ligne 430 (`DateTime.parse(e.startsAt).isAfter(now)`) n'est, lui, PAS fautif : `isAfter` compare des instants absolus, la comparaison UTC/local est correcte. Le défaut est strictement limité au rendu du bloc date (lignes 513 et 522). Portée : événements dont l'heure locale famille est inférieure à l'offset (00:00–02:00 à Paris l'été, 00:00–01:00 l'hiver) — fenêtre étroite, d'où le maintien en P2 malgré une donnée fausse affichée.

### C35 — Règle jumelle PHP/Dart des marqueurs A/B : jeux de tests identiques mais implémentations divergentes sur les espaces Unicode *(annoncé P3)*

`mobile/lib/features/custody/presentation/parent_initials.dart:64`

**Motif du rejet.** La moitié technique du constat est fausse, vérifiée en exécutant PHP sur le dépôt : `php -r 'var_dump(preg_match("/\s/u", "\u{00A0}"));'` renvoie 1. Le modificateur `u` de PHP active PCRE2_UTF **et** PCRE2_UCP, donc `\s` matche bien U+00A0 sans `(*UCP)` — l'affirmation « \s en PCRE/UTF-8 ne matche pas U+00A0 » est démentie. Conséquence : sur `" Élodie"` (NBSP en tête), `preg_split('/\s+/u', ..., 2)` renvoie `["", "Élodie"]` (vérifié), donc `ParentInitials::firstName` (backend/src/Web/ParentInitials.php:91-93) retourne `''` et `pair()` retombe sur `['A'=>'A','B'=>'B']` (ligne 55-57). Le web n'affiche donc JAMAIS le « caractère invisible mis en capitale » décrit comme panne : il affiche « A »/« B », un marqueur lisible et non chromatique. La panne annoncée n'est pas atteignable. Résidu réel mais bénin : côté Dart, `.trim()` supprime bien U+00A0 (vérifié : `' Élodie'.trim().codeUnits.first == 201`, soit « É »), donc le mobile afficherait « É » là où le web affiche « A ». Les deux clients restent lisibles et conformes à l'exigence non chromatique du cdc §8 ; aucun parcours n'est cassé et l'entrée exige un nom collé avec une espace insécable en tête (aucune normalisation côté backend — RegisterRequest.php:37-38 et MeProcessor.php:38 n'en font pas). Écart cosmétique de cohérence inter-clients, pas le défaut décrit.
